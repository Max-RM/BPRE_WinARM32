# l9d3d11 - Direct3D 9_1 shim for Bad Piggies::Rebooted (UWP ARM32)

Unity 2018.4 dropped the Direct3D feature-level 9.x render path. On a Tegra
3/4 tablet (Surface RT, Surface 2 - feature level 9_1) `UnityPlayer.dll` asks
for a device with the level list `[11_1 .. 10_0]`, gets nothing, and either
refuses to start or falls back to WARP (CPU rendering, a few frames per second).

`l9d3d11.dll` is a small forwarder that takes the place of `d3d11.dll` for the
game. It passes every call to the real system `d3d11.dll`, except that it

* makes `D3D11CreateDevice` succeed with a 9_1 device when the requested
  feature level is unavailable (on a real 10_0+ GPU it does nothing at all),
* swaps Unity's SM4/SM5 shaders for prebuilt `*_level_9_1` variants from
  `data\l9_replacements.bin` (matched by DXBC checksum),
* sanitises the texture/sampler/rasterizer/blend/depth-stencil descriptors to
  the 10Level9 rules and answers the caps queries with 9_1-safe limits.

Nothing in the game itself is modified - the package only repoints imports and
adds files. `scripts\Build-UWP-ARM32-L9D3D11-RT-Fix.ps1` produces the
ready-to-install appx; this folder holds everything that build needs. The game
executable keeps the name the project gives it (`BadPiggiesRebooted.exe` in the
tested package, `Bad PiggiesRebooted.exe` when the project is rebuilt), so the
build reads it from `AppxManifest.xml` instead of hard-coding it.

The finished package is published to `Publish\BPRE_UWP-ARM32-L9D3D11\` as
`Bad_PiggiesRebooted_<version>_ARM32_TegraPatch.appx`, next to the normal
`Bad_PiggiesRebooted_<version>_ARM32.appx` from `BPRE_UWP-ARM32`. Only the file
name differs - the identity inside is the same, so either build replaces the
other on the device.

```
l9d3d11_Fix\
  l9d3d11.dll            ARM32 shim, built from src\ (shipped so the package
                         script works without a compiler installed)
  build-l9d3d11.ps1      rebuilds l9d3d11.dll, verifies exports/imports
  build-l9d3d11.bat      double-click wrapper for the script above
  patch-pe.ps1           PE32 reader/patcher used by both scripts
  src\                   shim sources (l9shim.c + two includes + .def)
  data\                  l9_replacements.bin - the level-9 shader table
  vclibs\                VC143 ARM runtime, copied into the package app-local
  llvm-rt\               the compiler/linker used to build the shim
  loose\                 scripts packed into the appx root for installing an
                         unpacked copy (Install-Loose.bat/.ps1, Open-Saves.bat)
```

## Where every file came from

### src\ - the shim

| file | origin |
| --- | --- |
| `l9shim.c` | `Win32Craft_ARM\tools\badpiggies\l9shim.c` |
| `l9wrap.inc` | `Win32Craft_ARM\tools\badpiggies\l9wrap.inc` (device/vtable wrappers, state sanitisers) |
| `l9caps.inc` | `Win32Craft_ARM\tools\badpiggies\l9caps.inc` (in-memory caps correction inside UnityPlayer) |
| `l9shim.def` | `Win32Craft_ARM\tools\badpiggies\l9shim.def` (the three forwarded d3d11 exports) |

They come from the Win32Craft ARM compatibility project
(<https://github.com/Max-RM/Win32Craft_ARM>), where the shim was designed and
proven on a Surface 2. Only these four files are used here - the rest of that
project (host, probes, recon tools) is not part of this port. The full design
notes are in that repository (`games_recon\bad_piggies_hw-design.md`).

### data\l9_replacements.bin - the shader table

Produced by the Win32Craft shader recon
(`Win32Craft_ARM\games_recon\bad_piggies_shader_proto\auto\l9_replacements.bin`).
Format (`L9SW` v1): `"L9SW"(4) version=1(4) count(4)`, then `count` entries of
`checksum(16) offset(4) size(4)` followed by the `*_level_9_1` blobs. 121
replacements, generated by compiling the shaders Unity creates against
`ps_4_0_level_9_1`/`vs_4_0_level_9_1` and comparing the DXBC checksums. The
table is loaded from `Data\bp\l9_replacements.bin` next to the game exe.

### vclibs\ - the Visual C++ runtime for the device

| file | origin |
| --- | --- |
| all 8 DLLs | `%ProgramFiles%\Microsoft Visual Studio\2022\Community\VC\Redist\MSVC\14.44.35112\onecore\arm\Microsoft.VC143.CRT` |

`vcruntime140.dll`, `msvcp140.dll`, `msvcp140_1.dll`, `msvcp140_2.dll`,
`msvcp140_atomic_wait.dll`, `msvcp140_codecvt_ids.dll`, `vccorlib140.dll`,
`concrt140.dll`.

The Unity player imports the *framework* variants (`VCRUNTIME140_APP.dll`,
`MSVCP140_APP.dll`, `vccorlib140_app.dll`), which only exist inside the
`Microsoft.VCLibs.140.00` framework package. Windows 10 ARM32 build 15035
cannot deploy a newer dependency than the one in its image, so the packaging
script renames those imports to the plain names, ships these DLLs next to the
exe and removes the `PackageDependency` from `AppxManifest.xml`. The Universal
CRT (`api-ms-win-crt-*.dll`) is in-box on Windows 10, so nothing else is needed.

These exact 8 files were checked byte-for-byte against the working Win32Craft
package for the same game build. If you update Visual Studio, copy the new
`onecore\arm\Microsoft.VC143.CRT\*.dll` over this folder - but keep the
`14.44.*` set unless you can test on the tablet, because the CRT version must
match the one the IL2CPP player was built with.

### llvm-rt\ - the compiler

`clang.exe` + `lld-link.exe` are **rt2.1**, a community LLVM 23.1.1 build for
ARM32 Windows:

* release page: <https://github.com/hamed7ir/llvm-rt1/releases/tag/rt2.1-23.1.1>
* file: `rt2.1-23.1.1-rt2.1-arm32-win.tar.gz` (328 MB)
* SHA-256: `549A6FCF78A5999BFD94151DE9ED34CBFBAB9A6F5E686D53A4777CBC842EA8E5`
* `clang.exe --version` reports `Varan clang version 23.1.1-rt2.1
  (e240ad76c3a4429084c026fe0a9b0fce34025032)`

Taken from the unpacked release (`rt2.1-23.1.1-rt2.1-arm32-win\`):

```
bin\clang.exe  bin\lld-link.exe
bin\msvcp140*.dll  bin\vcruntime140*.dll      (the tools' own runtime)
lib\clang\23\include\                         (303 clang resource headers)
LICENSE.TXT  MODIFICATIONS.txt  RELEASE-NOTES.md
patches\rt21-vs-23.1.1.patch                  (the upstream diff)
licenses\libxml2-Copyright.txt
```

`README.md` of the release is kept as `UPSTREAM-README.md` so it cannot be
confused with this file. Everything else in the tarball (`libclang.dll`,
`clang-cl.exe`, `llvm-*` tools, `runtime\`, `staged\`) is not needed to build
one 16 KB DLL and was dropped to keep the repository small.

Licensing: `LICENSE.TXT` is the LLVM Apache-2.0-with-LLVM-exceptions license and
is shipped unchanged. `MODIFICATIONS.txt` lists the 16 patches, all of which are
ARM32 wrong-code/AAPCS fixes; the same diff is in `patches\`.

Why rt2.1 and not rt1.x or rt2: rt1.x is frozen on LLVM 18.1.8, and rt2 has two
known wrong-code bugs (0015/0018) that were fixed in rt2.1. The shim is small
but it runs inside Unity's device object, so a miscompile is silent and fatal.

## Rebuilding l9d3d11.dll

Requirements on the machine doing the build:

* Visual Studio 2022 with *Desktop development with C++* (only its headers are
  used - the MSVC ARM compiler is not needed),
* Windows 10 SDK **10.0.19041.0** with the ARM32 libraries
  (`Lib\10.0.19041.0\um\arm\kernel32.lib`, `armrt.lib`). The ARM32 SDK libraries
  were dropped after 10.0.22621, so a newer-only installation cannot build this.

Then, from this folder:

```
build-l9d3d11.bat              (double-click, or)
powershell -ExecutionPolicy Bypass -File .\build-l9d3d11.ps1
powershell -ExecutionPolicy Bypass -File .\build-l9d3d11.ps1 -Force
```

The script stops if `l9d3d11.dll` already exists unless `-Force` is given. It
finds the SDK and the MSVC headers itself (`vswhere`), or you can override them:
`-SdkRoot`, `-SdkVersion`, `-MsvcInclude`, or the `BPRE_MSVCINC` environment
variable. It compiles with

```
clang --target=thumbv7-pc-windows-msvc -march=armv7-a -mfpu=neon \
      -mfloat-abi=hard -O2 -ffreestanding -fno-builtin -fno-stack-protector \
      -D_WIN32_WINNT=0x0603 -DWINVER=0x0603 -c src\l9shim.c
lld-link /dll /machine:arm /subsystem:windows,6.02 /entry:DllMain \
      /nodefaultlib /brepro /timestamp:0 /def:src\l9shim.def \
      /out:l9d3d11.dll l9shim.obj kernel32.lib armrt.lib
```

and then proves the result: ARM32 machine type, **only** `KERNEL32.dll` in the
import table (the shim must not need a C runtime), and the exports
`D3D11CreateDevice`, `CreateDirect3D11SurfaceFromDXGISurface`,
`CreateDirect3D11DeviceFromDXGIDevice`.

**The SHA-256 of the DLL changes on every build** - `l9shim.c` logs
`__DATE__`/`__TIME__` in its first log line ("build <date> <time>"), which is
useful when a user reports a bug. Do not pin the hash; check the exports and
imports instead. Rebuild the package with
`scripts\Build-UWP-ARM32-L9D3D11-RT-Fix.ps1` after touching `src\`.

## Updating the compiler

1. Download the release tarball from
   <https://github.com/hamed7ir/llvm-rt1/releases> and verify it against the
   `SHA256SUMS` asset of the same release.
2. Unpack it (`tar -xzf` - Windows `tar.exe` handles `.tar.gz`).
3. Copy over, keeping the layout:
   `bin\clang.exe`, `bin\lld-link.exe`, `bin\msvcp140*.dll`,
   `bin\vcruntime140*.dll`, `lib\clang\<ver>\include\`, `LICENSE.TXT`,
   `MODIFICATIONS.txt`, `RELEASE-NOTES.md`, `patches\*`, `licenses\*`, and the
   release `README.md` as `UPSTREAM-README.md`.
   Note the resource headers move with the LLVM version
   (`lib\clang\23\include` today); remove the old version folder.
4. Run `build-l9d3d11.ps1 -Force`. It warns when `clang --version` is not
   `23.1.1-rt2.1`; that warning is a reminder, not a hard error, but a new
   compiler needs a new round of device testing before it is published.
5. Rebuild the package and test on the tablet.

## Updating the shader table or the game build

* The table is a plain `L9SW` v1 file; the shim only reads it. If a shader is
  missing its level-9 replacement, the shim writes `l9miss_<n>.dxbc` next to the
  log, which can be converted offline and added to the table.
* `src\l9caps.inc` patches UnityPlayer's in-memory caps object through three
  hard-coded RVAs (`0x0100776c`, `0x0100763a`, `0x0298ed40`). They only exist in
  the UnityPlayer.dll build this port ships
  (SHA-256 `E3530FD5D6CC0E431E5EDB69623B7C18E1A57A8013914D958C5F02711CB03793`).
  On any other build the patch is skipped **without an error** - that is why
  `Build-UWP-ARM32-L9D3D11-RT-Fix.ps1` refuses a different UnityPlayer.dll
  unless `-AllowDifferentUnityPlayer` is passed. If the game is rebuilt, the
  RVAs must be re-derived (see `l9caps.inc` and the Win32Craft design notes).

## Installing from an unpacked copy

`loose\` is copied verbatim into the root of the appx (the build script checks it
and fails if the files are not plain ASCII/CRLF or if the PowerShell script uses
anything Constrained Language Mode blocks). Unpack the appx into a normal folder
and run `Install-Loose.bat`:

* it refuses to start when the game is already installed, because Windows cannot
  replace an installed copy from a loose folder (0x80073CFB / 0x80073D06); it
  says to back the saves up with `Open-Saves.bat`, remove the app by hand and run
  it again,
* it removes `AppxSignature.p7x`, `AppxBlockMap.xml`, `AppxMetadata\`,
  `[Content_Types].xml` and `StoreManifest.xml` (they describe the original appx
  bytes and make `Add-AppxPackage -Register` fail) and then registers
  `AppxManifest.xml` with `-Register -ForceApplicationShutdown`,
* it refuses to register from the root of a drive (0x80073CF9) and warns when
  Developer Mode is off,
* it renames entries that an unpacker left percent-encoded. An .appx stores
  `Bad PiggiesRebooted.exe` as `Bad%20PiggiesRebooted.exe` and the folder
  `Data\Resources\unity default resources` as `unity%20default%20resources`;
  `makeappx unpack` decodes that, 7-Zip and Explorer do not. Without the repair
  `AppxManifest.xml` (`Executable="Bad PiggiesRebooted.exe"`) could not be
  registered and the player would not find its resources folder. The decoding is
  plain string arithmetic (`Repair-OpcNames` / `ConvertFrom-OpcName`), so it also
  works in Constrained Language Mode, and it does nothing when the names are
  already correct,
* `Open-Saves.bat` opens
  `%LOCALAPPDATA%\Packages\BadPiggiesRebooted_<hash>\LocalState` in a new
  Explorer window so `Progress.dat`, `Settings.xml`, `playerprefs.dat` and
  `contraptionsB\` can be copied by hand. `<hash>` comes from the signing
  certificate (`x0xr9mv5edyrp` for this build, another one - for example `...hj` -
  for a package signed with a different certificate), so the batch does not
  hard-code it: it tries the known name first, then any `BadPiggiesRebooted_*`
  package folder under `%LOCALAPPDATA%\Packages`, preferring one that already has
  saves. If the folder does not exist yet (the game has never run) it opens the
  package folder instead.

The scripts deliberately avoid `Add-Type`, `New-Object` and .NET method calls:
Windows 10 ARM32 build 15035 runs PowerShell in Constrained Language Mode. They
are ASCII-only because the device has no UTF-8 console. Keep them that way; the
package build validates it. Nothing here changes the signed appx path - the
published `Install.bat` / `Install.ps1` next to the appx are a separate, normal
package installation.

## Limitations

* ARM32 code cannot run on an x64 build machine - the final check always
  happens on a Surface RT / Surface 2 (or an ARM64 device with ARM32 support,
  where the shim is simply inactive).
* A 9_1 device still lacks features; a few cosmetic effects use a different
  shader (e.g. the IMGUI rounded-rectangle shader has no replacement in this
  table and falls back to Unity's default).
* The package has the same identity/version as the regular ARM32 build, so
  installing it replaces that build and vice versa.

## Logs on the device

`l9shim.log` is written to `%LOCALAPPDATA%\l9shim.log`; inside the app
container that lands in the package's own store, i.e. somewhere under
`%LOCALAPPDATA%\Packages\BadPiggiesRebooted_<hash>\` - search for
`l9shim.log` there. It records the GPU, the feature level the shim obtained,
how many shaders were swapped and any error, which is exactly what is needed to
fix a rendering problem.
